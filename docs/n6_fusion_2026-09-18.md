# STM32N6 위험도 융합 하드웨어 실증 (2026-09-18)

Pi가 기상·위치로 계산한 임계값을 STM32N6570-DK가 받아, 노면 분류 확률을 융합해
1차 경고를 판정하는 경로를 실제 하드웨어에서 검증했다.

## 구성

```
STM32N6570-DK ──[이더넷 1Gbps, 192.168.50.158]── Pi eth0 (192.168.50.1, DHCP 서버)
      └──[USB-C: ST-LINK/V3]── 데스크탑        └──[WiFi/학교망]── 데스크탑 (CARLA)
      └──[USB-C: 보조배터리]  ← 전원 보강 필수
```

**보조배터리가 필요하다.** 데스크탑 USB-A(5V 0.5~0.9A)만으로는 타깃 전압이 0.19V로
떨어져 SWD 연결이 끊긴다. 보조배터리를 반대쪽 USB-C에 꽂으면 3.28V로 정상화된다.
단 반대쪽 포트는 USB OTG이므로 **보조배터리만으로는 보드가 켜지지 않는다** — ST-LINK
케이블과 함께 둘 다 꽂아야 한다.

## 결과

### 보드 C 구현 vs `fusion.py` 참조 구현 — 전 케이스 일치
`scripts/n6_fusion_client.py --selftest`

| 케이스 | p_ice | 보드 risk | Pi risk | 차 | 보드 지연 |
|---|---|---|---|---|---|
| 클래스만 (반사도·차선 미학습) | 0.10 | 0.1000 | 0.1000 | 1.5e-09 | 5.10 µs |
| 클래스만 | 0.44 | 0.4400 | 0.4400 | 2.4e-09 | 3.94 µs |
| 클래스만 | 0.50 | 0.5000 | 0.5000 | 0 | 3.85 µs |
| 클래스만 | 0.92 | 0.9200 | 0.9200 | 1.7e-08 | 3.90 µs |
| 세 신호 모두 | 0.60 | 0.7100 | 0.7100 | 3.8e-08 | 4.12 µs |
| 세 신호 모두 | 0.20 | 0.1250 | 0.1250 | 1.5e-08 | 4.04 µs |

차이는 float32 반올림 수준이고 경고 판정도 전부 동일하다. 미학습 신호를 NaN으로
제외하면 `risk = p_ice`가 되는 재정규화도 양쪽이 같다.

### 기상 컨텍스트가 판정을 바꾼다 (같은 p_ice = 0.50)

| 상황 | prior | threshold | weights | 보드 판정 |
|---|---|---|---|---|
| 교량·새벽5시·−3℃·습도88% | 0.863 | **0.441** | (0.35,0.45,0.20) | **경고** level 2 |
| 평지·정오·+12℃·습도40% | 0.000 | 0.700 | (0.50,0.30,0.20) | 없음 level 0 |

같은 빙판 확률에 정반대 판정이 나온다. 이것이 프로젝트의 핵심 논지다.

### 링크 성능
- ping 3/3, 손실 0%, RTT 평균 0.323 ms
- UDP 왕복 RTT 260 µs ~ 5 ms (Pi 파이썬 측 지터 포함), 보드 내부 판정 4 µs 내외

## 프로토콜 (little-endian, packed)

| 방향 | 이름 | 형식 | 크기 |
|---|---|---|---|
| Pi → N6 | ctx | `<I5f` seq, threshold, alpha, beta, gamma, hysteresis | 24 B |
| 호스트 → N6 | infer | `<I6f` seq, p[4], spec, lane | 28 B |
| N6 → 송신자 | verdict | `<IfBBHI` seq, risk, alarm, level, pad, latency_ns | 16 B |

포트 5557 (protocol.py `PORT_N6_PUB`). 길이로 패킷 종류를 구분한다.
`spec`/`lane`에 **NaN**을 넣으면 그 신호를 제외하고 가중치를 재정규화한다 —
0을 "중립값"으로 넣으면 가중 합에서 최솟값이 되어 위험도 상한이 잘린다.

## 빌드·플래시 절차 (우리 워크스페이스)

```bash
# 워크스페이스: 데스크탑 ~/icepredict/fw/n6root/
#   Drivers, Middlewares 는 ~/STM32CubeN6 로 심링크 (SDK 원본 무변경)
#   프로젝트: Projects/STM32N6570-DK/Applications/NetXDuo/icepredict_n6/

export PATH=/opt/st/stm32cubeide_2.1.1/plugins/com.st.stm32cube.ide.mcu.externaltools.gnu-tools-for-stm32.14.3.rel1.linux64_1.0.100.202602081740/tools/bin:$PATH
cd ~/icepredict/fw/n6root/Projects/STM32N6570-DK/Applications/NetXDuo/icepredict_n6/STM32CubeIDE/FSBL/Debug
make all -j8

T=/opt/st/stm32cubeide_2.1.1/plugins/com.st.stm32cube.ide.mcu.externaltools.cubeprogrammer.linux64_2.2.400.202601091506/tools/bin
$T/STM32_SigningTool_CLI -bin Nx_WebServer_FSBL.bin -nk -of 0x80000000 -t fsbl \
   -o ~/icepredict/fw/out/icepredict_n6-trusted.bin -hv 2.3 -align -s
# BOOT1 오른쪽 (프로그래밍 모드)
$T/STM32_Programmer_CLI -c port=SWD mode=UR -hardRst \
   -el $T/ExternalLoader/MX66UW1G45G_STM32N6570-DK.stldr \
   -d ~/icepredict/fw/out/icepredict_n6-trusted.bin 0x70000000 -v
# BOOT0 왼쪽 + BOOT1 왼쪽 (실행) + USB 재연결
```

### 부팅 스위치
- **프로그래밍(굽기): BOOT1 오른쪽** (BOOT0 무관). 화면 검은 것 정상
- **실행: BOOT0 왼쪽 + BOOT1 왼쪽** + USB 재연결 또는 NRST
- 실행 모드에선 Debug Authentication으로 SWD가 잠긴다 ("No STM32 target found"가 뜨면 스위치를 확인할 것)

### 빠지기 쉬운 함정 (실제로 겪은 것)
1. **`-align` 필수.** 없으면 부트ROM이 이미지를 0x400 어긋나게 로드해 main에 도달하지 못한다
2. **`headless-build.sh`는 산출물을 못 만든다.** `make all -j8` + PATH에 CubeIDE 툴체인 추가가 되는 경로
3. **인클루드가 8단계 상대경로**라 프로젝트를 옮기면 전부 깨진다. SDK를 심링크한 같은 깊이의 루트(`n6root/`)가 해결책
4. **`subdir.mk`가 프로젝트 소스를 절대경로로 참조**한다. 복사만 하면 여전히 원본을 컴파일해서, 패치해도 바이너리가 안 바뀐다 (크기가 그대로인 것으로 발견). 프로젝트 경로만 우리 쪽으로 바꾸고 SDK 경로는 공유 유지
5. **`nx_udp_source_extract`의 포트 인자는 `UINT *`** (`ULONG *` 아님)
6. **nano.specs의 printf는 `%f`를 지원하지 않는다** — 천분율 정수로 찍는다

## 미해결

1. **NPU 추론 미배포.** ST Edge AI Core / X-CUBE-AI 미설치 (st.com 로그인 필요한 수동
   다운로드). 그래서 `infer` 패킷을 지금은 호스트가 대신 보낸다. INT8 양자화 붕괴
   (0.910 → 0.48) 재시도도 이것이 선행 조건이다
2. **반사도·차선 헤드 미학습** — 융합 가중치의 65%. 현재 NaN으로 제외되어 `risk = p_ice`
3. **CARLA 데모가 아직 단일 프로세스** — 융합을 보드로 뺀 분산 구조로 전환해야 한다
4. 게이트키퍼 스레드(포트 5005)는 이전 프로젝트 유산으로 남겨뒀다. 빌드 위험을 줄이려
   건드리지 않았으나, 우리 펌웨어에서는 제거하는 것이 맞다
