# RTOS 가 왜 필요한가 — 같은 코드로 잰 비교

심사에서 가장 먼저 나올 질문은 "그 계산 Pi 에서 하면 안 되나?" 다. 보드 펌웨어가 쓰는 바로 그 헤더(`fw/npu_lib/slip_core.h`)를 파이에서 컴파일해 **같은 코드**로 재서 답한다.

**속도가 쟁점이 아니다.** Pi 5(2.4 GHz Cortex-A76)가 STM32N6(800 MHz Cortex-M55)보다 평균은 당연히 빠르다. 실시간 제어는 평균이 아니라 **최악값**으로 설계한다.

## 1. 제때 깨어나는가 — 주기 지터

2차 방어는 주기적으로 IMU 를 받아 판정해야 한다. 연산이 아무리 빨라도 **깨어나는 시각이 늦으면 판정 자체가 늦는다.** cyclictest 와 같은 방식으로, 1 ms 주기를 절대시각 기준으로 자고 깨어난 실제 시각의 지연을 쟀다. 매 주기 보드와 같은 연산도 실제로 수행한다.

| 조건 | 표본 | 평균 지연 | p99 | p99.9 | **최대 지연** |
|---|---|---|---|---|---|
| Pi 5 + Linux · 유휴 | 20,000 | 69 µs | 463 µs | 2076 µs | **5790 µs** |
| Pi 5 + Linux · 부하 | 20,000 | 68 µs | 450 µs | 2123 µs | **5429 µs** |
| STM32N6 + ThreadX (참고: 응답 **전체**) | 49,405 | 12.4 µs | — | — | **22.6 µs** |

리눅스는 **아무것도 안 돌 때도** 최대 5790 µs 늦게 깨어난다. 부하가 걸리면 5429 µs 다. 보드는 깨어남·연산·응답을 **다 합쳐서** 22.6 µs 안에 끝낸다 — 리눅스 최악 깨어남 지연의 **256분의 1** 이다.

> **제어 주기와 견주면**: 2차 방어의 제어 주기는 20 ms 다. 리눅스의 최악 깨어남 지연 5.79 ms 는 그 주기의 **29 %** 를 먹는다. 보드의 전체 응답 22.6 µs 는 **0.11 %** 다.

> 거리로 옮기면 38 km/h(10.6 m/s)에서 5.79 ms 는 6.1 cm 다. 한 번의 지연만 보면 작다. 문제는 크기가 아니라 **그 값을 보증할 수 없다**는 것이다 — 측정한 20,000 회의 최댓값일 뿐, 다음 번에 더 늦지 않는다는 근거가 없다. 안전 논증은 '대개 빠르다'가 아니라 '이 값을 절대 넘지 않는다'여야 한다.

## 2. 연산 자체는 얼마나 걸리나

참고로 연산 구간(`slip_step2` + `slip_control2`)만 따로 잰 값이다. 여기서는 Pi 가 훨씬 빠르다 — 그래서 "보드가 빠르다"고 말하면 안 된다.

| 플랫폼 · 조건 | 표본 | 평균 | p99.9 | 최대 | 최대/평균 |
|---|---|---|---|---|---|
| STM32N6 + ThreadX (NPU 동시) | 49,405 | 12.42 µs | — | 22.60 µs | **1.8×** |
| Pi 5 + Linux · 유휴 | 50,000 | 0.085 µs | 0.093 µs | 2.59 µs | **30×** |
| Pi 5 + Linux · 부하 | 50,000 | 0.085 µs | 0.093 µs | 1.94 µs | **23×** |

Pi 가 평균 146배 빠르다. 그런데도 최악/평균이 30배로 벌어진다. 연산이 86 ns 로 워낙 짧아 선점당할 틈이 적은데도 그렇다 — 리눅스의 진짜 문제는 §1 의 깨어남 지연이다.

## 3. 보드가 스스로 증명하는 우선순위 선점

외부 비교 없이도 보드 데이터만으로 선점을 보일 수 있다. NPU 가 25.5 ms 짜리 추론을 돌리는 주행과, NPU 가 쉬는 주행을 나눠 보면 된다.

| 조건 | 주행 | 2차 방어 평균 응답 |
|---|---|---|
| NPU 유휴 | 50 | 10.9 µs |
| NPU 가 25.5 ms 추론 중 | 33 | 12.4 µs |

25.5 ms 짜리 작업이 같은 코어에서 도는데 **응답은 1.6 µs 밖에 안 늘어난다.** 선점이 없었다면 최악의 경우 추론이 끝날 때까지 기다려야 하므로 25,500 µs — **16376배** 차이다. ThreadX 가 융합 스레드(우선순위 3)로 NPU 프레임 스레드(우선순위 4)를 선점하기 때문이고, 이것이 이 설계에서 RTOS 가 하는 일이다.

## 4. RTOS 가 없다면 — 수퍼루프

우선순위 선점이 없으면 미끄러짐 검사는 추론이 끝나야 돈다. 보드의 NPU 추론이 25.49 ms 고정이므로(실사진 25,140 회 측정, 편차 0.5 %), 한 루프로 짜면 2차 방어의 응답 주기가 그만큼이 된다.

| 구조 | 2차 방어 응답 | 38 km/h 에서 밀리는 거리 |
|---|---|---|
| 수퍼루프 (추론 → 검사 순차) | 25.5 ms | 0.27 m |
| ThreadX 선점 (현재 설계) | 0.023 ms | 0.0002 m |

**1128배** 차이다.

참고로 파이에서 같은 int8 모델을 CPU 로 돌리면 추론이 평균 10.9 ms 다. 수퍼루프로 짜면 그 값이 응답 주기가 된다.

## 5. 무엇을 주장할 수 있고 무엇은 못 하나

| 주장 | 가능 여부 |
|---|---|
| "2차 방어 응답의 최악값이 유계다" | ✅ 49,405 샘플 실측, 최악 22.6 µs |
| "범용 OS 는 깨어남부터 늦는다" | ✅ 유휴에서도 ms 단위 지연, §1 |
| "우선순위 선점이 실제로 동작한다" | ✅ NPU 동시/유휴 비교, §3 |
| "보드가 Pi 보다 빠르다" | ❌ 연산은 Pi 가 훨씬 빠르다. 이렇게 말하면 안 된다 |
| "리눅스로는 불가능하다" | ❌ PREEMPT_RT 로 가능하다. **복잡도** 논거로 말해야 한다 |

## 재현

```
python3 scripts/deploy/rtos_latency_bench.py --n 50000 --cyc-n 20000
```

보드 원본은 `logs/board_wcet.jsonl`, 리눅스 원본은 `/tmp/bench_slip_*.txt` 와 `/tmp/bench_cyclic_*.txt` 다.
